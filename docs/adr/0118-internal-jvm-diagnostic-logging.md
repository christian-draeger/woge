# ADR 0118: Standardize internal JVM diagnostic logging

- Status: Proposed
- Date: 2026-11-24
- Decision owners: Woge maintainers
- Related issues: [#297](https://github.com/christian-draeger/woge/issues/297)

## Context

The maintained JVM adapters and development endpoints use JUL, Commons Logging, SLF4J and
`System.Logger` for Woge-owned operational diagnostics. These calls should obey the host's logging
settings, and a runtime failure should be traceable without sending application exceptions to logs.

## Decision

Pin `io.github.oshai:kotlin-logging-jvm:7.0.14` and `org.slf4j:slf4j-api:2.0.18` as implementation
dependencies in the modules that emit diagnostics. The kotlin-logging artifact targets Java 8
bytecode and declares Kotlin stdlib 2.1.21. Woge compiles on JDK 21 with Kotlin 2.4.10 and targets
Java 17. The upstream publication supplies no SLF4J API or provider. The SLF4J API pin matches
the Spring Boot 4.1.1 BOM. Use the JVM artifact only. The current 8.x release prints an initialization
message to stdout by default, outside the host's log levels. The 7.x choice requires no global
configuration changes. [7.0.14 artifact metadata](https://repo.maven.apache.org/maven2/io/github/oshai/kotlin-logging-jvm/7.0.14/kotlin-logging-jvm-7.0.14.pom)
· [SLF4J library guidance](https://www.slf4j.org/manual.html#libraries)

Use private kotlin-logging loggers with stable names under `dev.woge` and build messages inside
lazy lambdas. Use INFO for a process or handler startup summary, WARN for a recoverable
configuration issue and ERROR for an unexpected operation failure. Reserve DEBUG and TRACE for
opt-in troubleshooting. Expected request rejection, disconnect and cancellation retain their
existing control flow without additional logging.

Keep diagnostic values to bounded names, counts, protocol or runtime versions, and validated IDs
generated by the host. Runtime request failures report the existing `CorrelationId` where available.
That immutable value travels explicitly with the request or coroutine and requires no MDC state.
Pass only the safe ID to the logger. Keep request headers and bodies, form values, HTML,
credentials, tokens, exception messages and stack traces out of the standard diagnostics.
If a future site needs MDC, scope it with a coroutine context element and test isolation across
suspension, nested work, cancellation and failures before adopting it.

`WogeObserver` remains the structured event boundary in [ADR 0035](0035-framework-neutral-semantic-observation-port.md).
Metric, trace and development consumers use the typed events. Diagnostic output does not establish
an event contract. Public Woge signatures expose no logging API.

## Inventory

| Existing site | Woge logger | Diagnostic |
| --- | --- | --- |
| Spring MVC Servlet response handoff | `dev.woge.spring.mvc` | ERROR for unexpected response failures |
| Spring Boot autoconfiguration for MVC and WebFlux | `dev.woge.spring.boot.autoconfigure.WogeAutoConfiguration` | INFO for runtime configuration and WARN for a missing shared render identity secret |
| Ktor render identity configuration | `dev.woge.ktor.WogeKtorHandlers` | WARN for a missing shared render identity secret |
| Ktor page and deferred response preparation | `dev.woge.ktor.KtorResponses` | ERROR for unexpected failures before streaming |
| Development browser channel and MCP endpoint | `dev.woge.development.browser.DevelopmentBrowserChannel`, `dev.woge.development.mcp.DevelopmentMcpServer` | ERROR for unexpected local endpoint failures |
| Development launcher | `dev.woge.development.gradle.WogeDevelopmentMain` | ERROR for unexpected session failure |

The KSP compiler diagnostic port, Gradle task lifecycle output, `wogeDev` usage and expected
startup errors, lifecycle summaries, child process output, and the readiness handshake keep their
owning interfaces.
The reference deployment's sample observer demonstrates an application-owned sink. Test harness
output, frozen spikes, generated code, third-party diagnostics and the JavaScript client stay
outside the framework logger inventory. Modules without existing diagnostics need no logging
dependency.

## Alternatives considered

- Use SLF4J directly. It has fewer dependencies and an explicit supplier-based fluent API.
  Kotlin-logging offers straightforward lazy lambdas and a consistent Kotlin call form while
  still routing through SLF4J on the JVM.
- Wrap a logger in another Woge API. The current sites need only severity, category and message.
  Direct private facade use leaves the semantic boundary with `WogeObserver`.

## Consequences

Framework libraries publish the facade and SLF4J API on their runtime variants. Spring Boot keeps
the provider selected by its application. Ktor and other JVM applications choose one compatible
provider. Woge changes no application logging configuration. The standalone `wogeDev` process
receives its own JUL provider on the isolated `wogeDevTooling` classpath so local endpoint failures
stay visible. Production applications and their restartable development children retain their own
logging setup. See [production operations](../guides/production-operations.md#framework-diagnostic-logging)
and the [development loop](../guides/development-loop.md#troubleshooting).

## Follow-up

When upgrading the facade, repeat the isolated provider and level-filtering checks. Confirm that
initialization emits no unconditional output and that published runtime metadata remains
provider-free. Keep request correlation explicit when adding diagnostics to another host.
